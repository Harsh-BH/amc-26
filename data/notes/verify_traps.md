### HIGH — silently costs leaderboard points or wastes submissions

| # | Trap | Evidence | Mitigation |
|---|---|---|---|
| 7 | **"Pretrained weights = external data?" — genuinely ambiguous, argue both ways.** Fair Play clause: *"designed to test your ML and data science skills using only the provided training data."* Read literally, this bans any pretrained checkpoint (embedding models, LLMs) trained on outside corpora. But Constraint #5 (license+≤8B) only makes sense if pretrained models *are* allowed — a rule permitting specific licenses for something categorically banned is incoherent. The far more consistent reading: "only the provided training data" governs task-specific fine-tuning/features (no scraping business registries), while a static pretrained checkpoint is a model artifact, not "data." | Both clauses read verbatim from p.5-7 of the PDF just now. | Document every pretrained checkpoint's origin, license, and param count explicitly in the methodology doc so a reviewer sees you made the call deliberately — and cache/download all weights *before* the window closes, since fetching one mid-challenge is what would actually look like "external lookup" under review. |
| 8 | **Empty prediction on a non-singleton scores exactly 0.0, no partial credit for "close."** Verified: `f_beta(∅, {S2-1,S2-2}) == 0.0`. A blocking-stage bug that returns zero candidates for even a modest slice of non-singletons craters macro F_0.5 with zero warning signal from the format validator (which doesn't compute score). | Own metric check this turn + PDF formula p.6. Test profile: blocking is the stated recall ceiling. | Track "% of test S1 with 0 candidates" as a first-class pipeline health metric, separate from leaderboard score. |
| 9 | **F_0.5's 2× precision weighting means the F1-optimal threshold is *wrong* for this metric.** Reusing a tutorial's 0.5 threshold under-predicts how much precision is worth; optimal cutoff sits higher. | PDF p.6-7: formula + "F_0.5 rewards precision more than recall." Own check: 1-right+1-wrong (50% P) on 2 true = 0.5, vs perfect-P/20%-R = 0.556 — precision dominates. | Sweep threshold on a held-out split to directly maximize F_0.5, not F1/accuracy. |
| 10 | **France is unlabeled everywhere in train (0 examples) and its strongest train signal — postal-code blocking — barely exists there** (test profile: only 0.4-0.5% of France addresses carry a 5-digit code vs. the 94%-precision postal key train relies on). Any threshold "validated" only on a US/India holdout is unvalidated for ~15% of the real test set. | Test profile §4/§7, independently consistent with the PDF's own France description (p.1-2: legal-form/rue-avenue tokens, no postal reliance). | Build a small structural (not learned) sanity check for France — exact-name-token overlap as weak positives — purely to catch pipeline breakage, not to fit a real threshold. |
| 11 | **Public LB is a subset, private LB is "the remaining portion," and the two governing docs disagree on which one decides rank** (PDF: private only decides; guidelines: "both leaderboards"). Repeatedly submitting to chase the public number risks overfitting to its country mix while the metric that (at least partly) counts is the *other* split. | PDF p.6 vs guidelines p.1, both read verbatim. | Trust your own train-holdout F_0.5 as the primary signal; spend live submissions to catch format/pipeline bugs, not to hill-climb a threshold against the public subset. |
| 12 | **5-submissions/day cap has no stated reset time or timezone anywhere** — not in the PDF, not in the guidelines (both just re-read in full), not in the Unstop page per the rule-lawyer's grep. If the platform resets at UTC midnight vs. IST midnight, a late-evening IST submission could burn tomorrow's slot or fail to free today's. | Guidelines p.1: *"maximum of 5 submissions per day for over 3 days... after which the submit button will be disabled"* — no reset-time clause exists to quote. | Budget as if reset = midnight IST (the challenge's own stated timezone) and stop submitting well before 11:30 PM IST if you're relying on a same-day slot still being open. |
| 13 | **`candidate_pairs.tsv` is optional to get a local `PASS`, mandatory in the final zip, and used to audit blocking quality on the packages that get manually reviewed.** A team that only ever runs the validator against `matching_results.tsv` can ship a final zip missing it and never know until review. | `validate_submission.py`: absence only warns, never fails an exit code (per rule-lawyer's read, confirmed by PDP's own "not scored... we use it to analyse blocking quality" framing, p.4). | Add your own hard-fail check for `output/candidate_pairs.tsv` existing before zipping — don't rely on the official validator's exit code alone. |
| 14 | **`--check-ids` loads ~10M IDs into a Python set, not the "~1.7M" the validator's own docstring implies** — on a box already noted as RAM-tight (~5GB free, this exact task's own constraint). | `test_source2`+`test_source3` = 4,887,273 + 5,082,316 ≈ 9.97M rows, both loaded by `--check-ids`. | Budget ~10M short strings (not 1.7M) when running `--check-ids` locally; if RAM is tight, validate format-only first and run `--check-ids` separately. |

### MEDIUM — data-quality traps that quietly degrade the model

| # | Trap | Evidence | Mitigation |
|---|---|---|---|
| 15 | **18% of India true pairs cross Devanagari/Latin script** — a Latin-only string-similarity matcher misses these outright. Romanization is fine; a *lookup-service* romanizer risks brushing against the external-data ban. | Train profile §5. | Use a rule-based/ICU transliteration scheme (algorithmic, no external lookups), not a hosted API. |
| 16 | **Literal `NULL`/`<NULL>` placeholder strings in ~2-3.7% of S2/S3 addresses**, distinct from genuine empty strings — silently poison text-similarity features if not cleaned, and are invisible to `validate_submission.py` (it never reads `business_address` content). | Train profile §10, test profile §6, both quantified. | Strip literal `NULL`/`<NULL>` tokens to true-empty before featurization — one regex, cheap. |
| 17 | **`\|`-joined name/website fields** (~0.24-0.3% of S2/S3 names, e.g. `"Foo Corp \| www.foo.com"`) — same silent-corruption risk on the name side. | Train profile §10, test profile §6. | Split on the literal `\|` before tokenizing names. |
| 18 | **Landmark-keyword false positives**: `"Opp, AL"` in a real address is a town-name fragment, not the word "Opposite" — a naive `"near"/"opp"/"behind"` keyword feature will misfire on this class of example. | Train profile §9 (`Tober's Marketing Inc` cluster). | Test any landmark-keyword feature against real matched-cluster examples before trusting it, not just synthetic ones. |
| 19 | **Most of the score lives in recall on multi-match clusters, not "first match wins."** Perfect-precision oracle with exactly 1 correct match/entity only reaches ~69.6% macro F_0.5 vs. 100% ceiling — most non-singletons need 2-5+ correct matches for full credit. | Train profile §8 (oracle calc). | Don't stop tuning once precision is clean — recall on multi-match S1 entities is the remaining ~30 points. |
