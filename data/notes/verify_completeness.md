## The task's own named questions — resolved as far as sources allow

**1. Daily-cap reset time — OPEN.** Guidelines PDF: *"Each team can make a maximum of 5 submissions per day for over 3 days of the hackathon, after which the submit button will be disabled."* No source states what timezone/hour boundary defines "a day." Strong inference (not a quote): the whole window is denominated in IST (`"25th September 2026, 12:00 AM IST to 27th September 2026, 11:59 PM IST"`), so midnight IST is the likely reset, but this is never stated. Also newly found and **missed by all five reports**: `api_001`/`api_002` both carry `"grace_period": 15` on the round object — unexplained in any prose source, plausibly a 15-minute late-upload grace window, but unconfirmed. Who can answer: Google Form.

**2. Does each leaderboard submission need the code zip? — INCONSISTENT, not just "partial" (upgrading Rule Lawyer's contradiction #4 to a directly-relevant answer).** The rendered submission form (`unstop_play_page.txt`) shows two upload widgets — *"Upload Matching Results File"* (TSV) and *"Upload Code File"* (zip) — both above one **single** *"Submit & Evaluate"* button, i.e. structurally one action requiring both files. The PDF's *Submission Requirements* section instead frames these as two separate, differently-timed deliverables: *"1. Leaderboard (during the challenge): upload `matching_results.tsv`... 2. Final submission package: submit the single zip..."* The API's `"no_of_submissions_file_allowed": 1` conflicts with either two-widget reading. None of the five reports resolves which governs, and it matters practically (up to 5/day × 3 days — is a full code zip expected on every one of those ≤15 uploads, or once at the end?). Who can answer: Google Form.

**3. team_name for the zip — OPEN, not previously raised in any of the five reports.** `<team_name>_submission.zip` appears in the PDF/README as a filename pattern only; nothing defines what string that is — Unstop-registered team display name? Sanitized (spaces→underscores)? `Documentation_template.md` has a free-text `**Team Name:** [Your Team Name]` field but that's the doc, not the zip filename. The API surfaces a numeric `team_id: 59311981` (from `api_002`'s `teamid`/`teamUniqueId`), which is clearly not a human-readable name. No source ties these together.

**4. What counts as "final model"? — OPEN, and it interacts with a real risk another report already flagged.** Constraint #5, verbatim: *"Final model should be a MIT/Apache 2.0 License model and up to 8 Billion parameters."* Undefined: (a) does this cover only the match/no-match decision model, or every model touching the pipeline including an embedding model used purely for blocking/features; (b) is the 8B cap per-model or cumulative across an ensemble (e.g. a separate blocking embedder + a separate classifier, each <8B but combined over). This directly bears on the REPO FIT report's `docs/EMBEDDINGS.md` finding — see below, that finding is itself somewhat overconfident given this ambiguity.

**5. Is fine-tuning allowed? — OPEN, never mentioned in any source (positively or negatively).** Only two constraints touch models at all: the license/8B-param rule (#5) and the external-lookup ban, which is about looking up *business identity data*, not about how a model's weights were produced. Fine-tuning on the *provided* training data doesn't obviously trip either rule, but no source confirms it, and no source says whether a fine-tuned checkpoint still counts as "a MIT/Apache 2.0 License model" once you've retrained it (an Apache-2.0 base model's license generally does permit fine-tuning and redistribution, but that's inference from general OSS-license knowledge, not from a challenge source).

**6. Can an LLM ≤8B Apache model like Qwen be used as the matcher? — RESOLVED at the structural/rule level, with a caveat.** Constraint #5's wording is architecture-agnostic — it says "a MIT/Apache 2.0 License model and up to 8 Billion parameters," not "a classifier" — so nothing in the text restricts *what kind* of model makes the final call; an Apache-2.0-licensed ≤8B LLM run locally (e.g. as an LLM-as-judge on candidate pairs) satisfies the letter of the constraint as written, same as any other model type, **provided it does no external API call** (a hosted LLM endpoint would collide with the external-services ban, a local weights-in-process LLM would not). One thing genuinely unaddressed by any source: no inference-time/compute budget is stated anywhere for the scorer (checked `*.txt` sources for "time limit," "timeout," "GPU," "compute budget" — zero hits), so there's no documented ceiling on how slow an LLM-per-pair matcher over the blocked candidate set is allowed to be; that's a self-imposed engineering constraint, not a rule.

**7. Can we use TEST S2/S3 records unsupervised, e.g. for TF-IDF fitting? — OPEN, and worth quoting precisely because the exact phrasing is ambiguous.** The only related text, in *Fair Play*: *"This challenge is designed to test your machine learning and data science skills using only the provided training data."* Read literally this says *training* data, not *training and test* data — which could be read as forbidding any statistics fit on the test records (a classic transductive-learning question), even though the test records are the challenge's own provided data, not external. It's much more likely this line is contrasting "provided data" vs. "external internet data" (the whole surrounding section is about external lookups), not policing train/test statistical leakage — but nothing confirms that reading. Given the "no external data lookup" section's own bullet list of *examples* never mentions test-set feature fitting at all, this is a real gap. Google Form is the right channel given the disqualification stakes.
