## CONTRADICTIONS between sources

1. **Rejection vs. score-lowering for unknown matched IDs.** PDF/README: "will be rejected." Validator docstring: "only lowers your score rather than being rejected by the scorer... a diagnostic, not a gate." *Resolution:* the validator's phrasing is the more specific, mechanically-detailed description of what the live scorer actually does (it reads like it was written by whoever built the scorer, describing real behavior), so it's likely the technically accurate one — but because the two texts genuinely conflict and the cost of guessing wrong is disqualification-adjacent, treat the PDF's stricter "will be rejected" framing as the safe target to comply with rather than relying on the validator's softer claim.

2. **Public/private leaderboard weighting for final ranking.** PDF: "Final Rankings: The final decision will be based on the private leaderboard." Guidelines: "Evaluation and shortlisting will be based on performance across both leaderboards." *Resolution:* genuinely unresolved from text alone — these may describe two different steps (a numeric tie-break vs. a holistic top-100 review that also weighs the doc and eligibility per guidelines), but there's no source that reconciles them. Recommend routing this exact question through the Google Form rather than assuming either wins.

3. **"1-2 page" doc vs. "no page limit."** Guidelines PDF *and* the API's generic round-level `display_text` (identical text in both `api_001` and `api_002`, attached to round id 290344, `updated_at: 2026-09-21T21:20:59`) say 1-2 pages. ## VALIDATOR notes — `validate_submission.py`

**Enforces (hard errors, exit 1):**
- File readable as valid UTF-8 (else a specific, actionable error — not a silent pass-or-crash).
- Header must be tab-delimited with exactly the 2 expected columns in order; comparison is **case-insensitive and per-cell-whitespace-stripped** (`c.strip().lower()`), but a header with commas-but-no-tab is caught with a specific "looks like a CSV" message; an extra/missing column (e.g. a stray trailing tab producing a phantom 3rd header cell) fails the header check.
- No duplicate `source1_entity_id` rows.
- No duplicate IDs within one row's ID list.
- No `S1-` IDs inside a match/candidate list (self-match).
- Every ID in a list must start with `S2-`/`S3-` — this **incidentally** also catches leading whitespace on an individual list item (`" S2-193"` fails `startswith`), but is reported as a generic "wrong prefix" error, never explicitly diagnosed as a whitespace problem.
- Every S1 entity in `test_source1.tsv` must appear exactly once; extra rows for unknown S1 IDs are also flagged.
- Optional (`--check-ids`): every matched/candidate ID must exist in `test_source2/3.tsv`.
- Soft, never-fails warning if a matched ID is absent from `candidate_pairs.tsv`.

**Does NOT enforce — real gaps that could pass the validator but bite in the actual scorer/submission:**
- **Leading/trailing whitespace on the `source1_entity_id` column itself** is never stripped (`s1, tab, rest = line.partition(DELIM)` uses `s1` raw) — a padded ID like `" S1-00001"` silently becomes a *different* string, surfacing only as confusing "required S1 entity missing" + "row using an S1 ID not in test set" noise, never diagnosed as whitespace.
- **A UTF-8 BOM** is not stripped (`encoding="utf-8"`, not `"utf-8-sig"`) — it glues to the first header cell and fails the header check with a cryptic `['\ufeffsource1_entity_id', ...]` message rather than a clear "remove the BOM" hint. It does fail loudly, just not clearly.
- **CRLF line endings are actually a non-issue** here (worth calling out since it's a classic TSV gotcha elsewhere): Python's default text-mode universal-newlines translation converts `\r\n`→`\n` transparently on read, so CRLF-terminated submissions parse fine.
- **Missing trailing newline** on the last line is fine — file iteration handles it.
- **Genuinely blank lines** are silently skipped with zero warning, anywhere in the file — could mask a truncated/corrupted file.
- **`candidate_pairs.tsv` absence only warns, never fails** — a team can get a clean `PASS` (exit 0) from a local run with no `candidate_pairs.tsv` at all, even though it's mandatory in the final submission zip. `PASS` here is not proof the final zip is complete.
- **Nothing about the rest of the submission zip** is checked: no verification of `code/business_entity_resolution/{src/,README.md,requirements.txt}` presence, no model-license check, no parameter-count check, no check that the code actually reproduces the two output files. All of that is manual, later ("the top teams' packages are reviewed in detail").
- **No score computation at all** — `PASS` says the shape is submittable, says nothing about F_0.5 quality.
- **No validation of `business_name`/`business_address`/`country` content** — it only ever reads the `entity_id` column from source files.
